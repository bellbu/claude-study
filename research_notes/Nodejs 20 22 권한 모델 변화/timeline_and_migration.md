## Q1. Chronological list of permission-model changes in 20.x, 21.x, 22.x and 23.x (with backports)

### Takeaway
The Permission Model arrived in v20.0.0 as `--experimental-permission`, marked Stability 1 (Experimental). It moved to 1.1 "Active development" in 21.0.0 and 20.10.0. In 21.6.0 and 20.12.0 it gained relative paths and `--allow-addons`. In 22.3.0 and 20.16.0 it gained `--allow-wasi`. It became Stable (2) under the new flag name `--permission` in 23.5.0, and that change was backported to 22.13.0, which keeps `--experimental-permission` as an alias. Later 22.x releases (22.17 and 22.18) added an implicit read grant for entry points, propagation of the flags to spawned processes, and `permission.has('addon')`. A steady run of security releases closed bypasses on every line.

This is the first release with Stable status and the `--permission` flag; it reached 22.13.0 about three weeks later — [CHANGELOG_V23](https://github.com/nodejs/node/blob/main/doc/changelogs/CHANGELOG_V23.md)
- **23.6.1 (2025-01-21)**: CVE-2025-23083 (InternalWorker). **23.7.0**: doc for InternalWorker, history and npx. **23.8.0**: permission.cc error handling ([#56904](https://github.com/nodejs/node/pull/56904)) — [CHANGELOG_V23](https://github.com/nodejs/node/blob/main/doc/changelogs/CHANGELOG_V23.md)

**After 22.x (context only, not in 22.x)**
- The permissions.md on `main` documents features that the v22.x docs lack: `--allow-net`, `--allow-env`, `--allow-inspector`, `--allow-ffi`, `--allow-openssl-store`, a `--permission-audit` mode that publishes violations to `node:diagnostics_channel` instead of throwing, and `permission.drop()` — [permissions.md main](https://github.com/nodejs/node/blob/main/doc/api/permissions.md). The v22.x cli.md lists only `--allow-fs-read`, `--allow-fs-write`, `--allow-child-process`, `--allow-worker`, `--allow-wasi` and `--allow-addons` under `--permission` — [cli.md v22.x](https://github.com/nodejs/node/blob/v22.x/doc/api/cli.md)

### Inferences
- The task brief mentions a "wildcard removal". I found no evidence of one up to the latest 22.x. The v22.x permissions.md still documents mid-path wildcards ("`--allow-fs-read=/home/test*` will allow read access to everything that matches the wildcard… `/home/*.js` will work similar to `/home/*`"). What changed was the removal of **comma-separated** path lists in 20.7.0 (#49047), plus wildcard *bug* fixes (CVE-2024-21890 and #51209). The brief may be mixing these up, or it may refer to a post-22 change I did not verify.
- Nearly every feature reached the 20.x line as a backport: addons and relative paths in 20.12.0, WASI in 20.16.0. The **stabilization and rename (#56201) did not**. That is the main 20-to-22 difference.
- Many permission fixes came through embargoed node-private PRs in security releases. "Behavior got stricter" changes (e.g. futimes, fchmod and fchown now blocked; symlink APIs now needing full read and write) arrive in patch releases on both lines, not only in minors.

### Gaps
- I could not confirm whether 22.13+ prints a deprecation or experimental warning when the `--experimental-permission` alias is used. The source shows a plain `AddAlias`, which suggests no warning, but I did not test it.
- I did not check the date or contents of the 20.x end-of-life notice. Per the release schedule 20.x reached EOL around April 2026, but I did not fetch a source for that.
- I did not list every 21.x patch; only the permission entries found by the changelog grep are included.

## Q2. Breaking or behavior changes when moving scripts and CI from Node 20 to Node 22

### Takeaway
The flag name is the most visible change. On 20.x only `--experimental-permission` exists. 22.13+ documents `--permission` and keeps the old name as an alias, but 22.0 to 22.12 accept only `--experimental-permission`. Beyond that, a migrated script needs `--allow-wasi` if it uses WASI (and on 20.16+ it already does). Comma-separated `--allow-fs-*` lists have not worked since 20.7. Behavior differs depending on which 22.x minor is in use (implicit entry-point read in 22.17, flag propagation to spawned processes in 22.18). `--experimental-policy` is gone entirely from 22.2.0.

### Cited Findings
- **Flag name.** v20.x registers only `--experimental-permission` ([node_options.cc v20.x](https://github.com/nodejs/node/blob/v20.x/src/node_options.cc)). v22.x registers `--permission` plus `AddAlias("--experimental-permission", "--permission")` ([node_options.cc v22.x](https://github.com/nodejs/node/blob/v22.x/src/node_options.cc)). The rename landed in 22.13.0 via #56201 ([CHANGELOG_V22](https://github.com/nodejs/node/blob/main/doc/changelogs/CHANGELOG_V22.md)). Both names are allowed in `NODE_OPTIONS` (`kAllowedInEnvvar`; the cli.md NODE_OPTIONS allow-list still includes `--experimental-permission`) — [cli.md v22.x](https://github.com/nodejs/node/blob/v22.x/doc/api/cli.md)
- **Stability and warnings.** 20.x docs mark the model "Stability: 1.1 - Active development", and the old examples show `ExperimentalWarning: Permission is an experimental feature`. 22.13+ marks it "Stability: 2 - Stable" and drops the warning example — [permissions.md v20.x](https://github.com/nodejs/node/blob/v20.x/doc/api/permissions.md); [PR #56201 diff](https://github.com/nodejs/node/pull/56201)
- **Path syntax.**
  - Comma lists are no longer split (since 20.7.0, #49047); repeat the flag instead ([PR #49047](https://github.com/nodejs/node/pull/49047)).
  - Relative paths work from 20.12.0 and 21.6.0 (#50758) ([CHANGELOG_V20](https://github.com/nodejs/node/blob/main/doc/changelogs/CHANGELOG_V20.md)).
  - Valid arguments in 22.x are `*`, relative paths (resolved against the CWD) and absolute paths.
  - An existing directory gets an implicit trailing `*`. A directory that does not exist yet needs an explicit `/dir/*`.

  The last three points come from [permissions.md v22.x](https://github.com/nodejs/node/blob/v22.x/doc/api/permissions.md).
- **New required flags.**
  - `--allow-addons` (20.12 and 21.6): without it, native addons throw `ERR_DLOPEN_DISABLED`.
  - `--allow-wasi` (22.3 and 20.16): without it, WASI throws `ERR_ACCESS_DENIED`.
  - `--allow-child-process` and `--allow-worker` have existed since 20.0.0.

  Source: [cli.md v22.x](https://github.com/nodejs/node/blob/v22.x/doc/api/cli.md); [PR #53124](https://github.com/nodejs/node/pull/53124)
- **Entry point.** Before 22.17.0, `node --permission index.js` fails with `ERR_ACCESS_DENIED` / `FileSystemRead` on the entry file unless you pass, for example, `--allow-fs-read=./index.js` (this is what the 20.12.0 release notes recommend). From 22.17.0 the entry point and `-r` preloads are readable implicitly (#58579) — [CHANGELOG_V20](https://github.com/nodejs/node/blob/main/doc/changelogs/CHANGELOG_V20.md); [CHANGELOG_V22](https://github.com/nodejs/node/blob/main/doc/changelogs/CHANGELOG_V22.md)
- **Child processes.** The 20.x docs say "The model does not inherit to a child node process or a worker thread." The 22.x docs say only "does not inherit to a worker thread." Since 22.18.0, spawn and spawnSync propagate the permission flags (fork already did), unless the child gets explicit args or NODE_OPTIONS (#58853) — [permissions.md v20.x](https://github.com/nodejs/node/blob/v20.x/doc/api/permissions.md); [permissions.md v22.x](https://github.com/nodejs/node/blob/v22.x/doc/api/permissions.md); [PR #58853](https://github.com/nodejs/node/pull/58853)
- **Error semantics.**
  - The error code stays `ERR_ACCESS_DENIED`, with `permission` and `resource` properties ([permissions.md v22.x](https://github.com/nodejs/node/blob/v22.x/doc/api/permissions.md)).
  - Since 22.1.0 and 20.14.0, async APIs report the error asynchronously (#52730).
  - In 22.16.0 the message became more descriptive (#57585), so tests that match exact message text may break ([CHANGELOG_V22](https://github.com/nodejs/node/blob/main/doc/changelogs/CHANGELOG_V22.md)).
- **Runtime API.** `process.permission.has(scope[, reference])` is unchanged. It accepts a Buffer reference since 22.7 and 20.18 (#54104), and the `'addon'` scope since 22.18.0 (#58951) — [CHANGELOG_V22](https://github.com/nodejs/node/blob/main/doc/changelogs/CHANGELOG_V22.md)
- **Constraints that still apply in 22.x:**
  - `--env-file`, `--openssl-config` and `v8.setFlagsFromString` act before or outside the model.
  - OpenSSL engines cannot be requested at runtime.
  - Existing file descriptors bypass the model.
  - Run-time loadable SQLite extensions are blocked.
  - Symlinks are followed even outside the granted paths.

  Source: [permissions.md v22.x](https://github.com/nodejs/node/blob/v22.x/doc/api/permissions.md)
- **npx usage** (docs added in 22.14 and 20.19.5): `npx --node-options="--permission --allow-fs-read=$(npm prefix -g)" pkg`, or point the read grant at `$(npm config get cache)` — [permissions.md v22.x](https://github.com/nodejs/node/blob/v22.x/doc/api/permissions.md)
- **Policy.** `--experimental-policy` and `--policy-integrity` are removed in 22.2.0+ (#52583). The v22.x cli.md no longer documents either — [CHANGELOG_V22](https://github.com/nodejs/node/blob/main/doc/changelogs/CHANGELOG_V22.md); [cli.md v22.x](https://github.com/nodejs/node/blob/v22.x/doc/api/cli.md)

### Inferences
- Practical migration checklist:
  1. Pin 22.x at 22.13 or later (ideally the latest 22.23.x for the CVE-2026-58043 fix) and switch `--experimental-permission` to `--permission`. If one CI matrix must run both 20 and 22, keep `--experimental-permission`: it works on every 20.x and every 22.x thanks to the alias.
  2. Replace any comma-joined `--allow-fs-read=a,b` with repeated flags.
  3. Add `--allow-wasi` and `--allow-addons` where those features are used.
  4. Do not count on the implicit entry-point read or spawn propagation unless the minimum version is 22.17 or 22.18. Keep an explicit `--allow-fs-read=./entry.js` for portability back to 20.12+.
  5. Remove `--experimental-policy` and `--policy-integrity`. Node 22.2+ rejects them as unknown options, which I infer from their removal; I did not test it.
  6. Assert on `err.code === 'ERR_ACCESS_DENIED'`, not on the message text.
- Because security patches keep tightening checks (futimes, fchmod and fchown, symlink APIs, trace events, report paths), an app that "worked" on an older 22.x can start throwing ERR_ACCESS_DENIED after a patch upgrade. CI should not assume patch releases leave permission behavior unchanged.

### Gaps
- I did not test the exact error or exit behavior for `--experimental-policy` on 22.2+.
- I found no official Node.js blog post dedicated to migrating the permission model; the guidance above comes from the changelogs and docs.

## Q3. How the Permission Model relates to the removed Policy (`--experimental-policy`) mechanism

### Takeaway
They were two separate mechanisms in the same docs page. "Module-based permissions" (Policy) checked code integrity at load time via a manifest. "Process-based permissions" (the Permission Model) restrict what the running process can reach. Policy was doc-deprecated in 22.0.0 and 20.13.0 (#52602) and removed in 22.2.0 (#52583), because maintainers concluded it added little protection under the threat model. Its section was removed from permissions.md in 22.7.0 (#54266). The Permission Model is not a drop-in replacement for integrity checks.

### Cited Findings
- The 20.x permissions.md lists both: "Module-based permissions control which files or URLs are available to other modules during application execution", enabled via `node --experimental-policy=policy.json app.js`, with `--policy-integrity="sha384-..."` to protect the manifest, and SRI integrity checks on every loaded resource. It is listed next to "Process-based permissions", the Permission Model — [permissions.md v20.x](https://github.com/nodejs/node/blob/v20.x/doc/api/permissions.md)
- The 20.x docs say Policy "focus[es] on preventing malicious code from ever being fully loaded into the application in the first place", in contrast to "runtime-based models that may restrict capabilities once the code is loaded" — [permissions.md v20.x](https://github.com/nodejs/node/blob/v20.x/doc/api/permissions.md)
- Removal rationale, from issue #52575 "Remove --experimental-policy" (Rafael Gonzaga): the docs said "approval of the module integrity in the policies threat model implies they are allowed to muck with and even circumvent security features once loaded… once a module is loaded, they have the keys to the castle." After reviewing security reports, he did not think "it provides much additional protection against our threat model", and he notes it "was developed _before_ we had a threat model" — [Issue #52575](https://github.com/nodejs/node/issues/52575)
- Timeline: doc-deprecated in 22.0.0 and 20.13.0 (#52602); removed in 22.2.0 (#52583); policy mentions removed from security info in 22.4.0 and 20.16.0 (#53249); module-based permission doc removed in 22.7.0 (#54266) — [CHANGELOG_V22](https://github.com/nodejs/node/blob/main/doc/changelogs/CHANGELOG_V22.md); [CHANGELOG_V20](https://github.com/nodejs/node/blob/main/doc/changelogs/CHANGELOG_V20.md)
- Policy kept producing its own CVEs on 20.x, for example CVE-2023-30581 (`mainModule.__proto__` bypass, 20.3.1), process.binding and Module.constructor bypasses (20.5.1), and a tamper-proof integrity-check fix (20.8.1). 20.19.0 "disable require(esm) for policy and network import" ([#56927](https://github.com/nodejs/node/pull/56927)) — [CHANGELOG_V20](https://github.com/nodejs/node/blob/main/doc/changelogs/CHANGELOG_V20.md)
- The current deprecations.md on `main` has no DEP entry for `--experimental-policy`. Grepping for "policy" finds only the unrelated `--force-node-api-uncaught-exceptions-policy` — [deprecations.md](https://github.com/nodejs/node/blob/main/doc/api/deprecations.md)

### Inferences
- The task brief says Policy was removed "around v22/v23". The precise answer is **v22.2.0** (2024-05-15). It was never removed from 20.x, which kept `--experimental-policy` (deprecated) to end of life.
- Users who depended on Policy integrity checks have no in-core replacement in 22.x. The Permission Model limits resource access rather than verifying code. Integrity has to come from outside Node (lockfile integrity, signed artifacts, read-only filesystems, OS sandboxing). This is my inference; Node gives no official replacement guidance.

### Gaps
- I could not find a numbered DEP code for the policy deprecation; it appears to have been documentation-only.

## Q4. What the docs and the Security team say the Permission Model is and is NOT

### Takeaway
Official Node.js sources call the Permission Model a "seat belt" for **trusted** code that guards against accidental access. It is explicitly not a sandbox against malicious code, because the Node.js threat model trusts all code it is asked to run, dependencies included. Stabilizing it in #56201 did not change this framing; the PR restates it ("Defense in Depth", "like seatbelts").

### Cited Findings
- The docs (v20.x and v22.x) say: "This feature does not protect against malicious code. According to the Node.js Security Policy, Node.js trusts any code it is asked to run." And: "The permission model implements a 'seat belt' approach, which prevents trusted code from unintentionally changing files or using resources that access has not explicitly been granted to. It does not provide security guarantees in the presence of malicious code. Malicious code can bypass the permission model and execute arbitrary code without the restrictions imposed by the permission model." — [permissions.md v22.x](https://github.com/nodejs/node/blob/v22.x/doc/api/permissions.md)
- The docs also say the model "does not guarantee that users will not be able to access the file system through other means, such as through the `node:sqlite` module", and that "Using existing file descriptors via the `node:fs` module bypasses the Permission Model" — [permissions.md v22.x](https://github.com/nodejs/node/blob/v22.x/doc/api/permissions.md)
- Known limitation: "Symbolic links will be followed even to locations outside of the set of paths that access has been granted to. Relative symbolic links may allow access to arbitrary files and directories." — [permissions.md v22.x](https://github.com/nodejs/node/blob/v22.x/doc/api/permissions.md)
- PR #56201 (Rafael Gonzaga, Security WG):
  - "We've leaned into a 'Defense in Depth' approach—recognizing that no single feature will let you run untrusted code safely. Instead, these features are like seatbelts: they reduce risk significantly (let's say 90% of cases, though that's not a hard number) but won't stop everything. This aligns with our threat model."
  - On symlinks: they "isn't fixable due to how the Permission Model relies on file paths, making TOCTOU issues theoretically possible", and "even Deno's permission system has similar behaviour".
  - Mitigating point: "The Permission Model blocks symlink creation by default."

  Source: [PR #56201](https://github.com/nodejs/node/pull/56201)
- SECURITY.md threat model: "Node.js trusts everything else", including "The code it is asked to run, including JavaScript, WASM and native code, even if said code is dynamically loaded, e.g., all dependencies installed from the npm registry… The code run inherits all the privileges of the execution user." It also trusts "Any connection used for inspector (debugger protocol)" and "The file system when requiring a module", and says "The `node:wasi` module does not currently provide the comprehensive file system security properties provided by some WASI runtimes." — [SECURITY.md](https://github.com/nodejs/node/blob/main/SECURITY.md)
- SECURITY.md still treats bypasses of a "common security control such as … permission enforcement" as needing private reporting, which explains the long series of permission-model CVEs listed in Q1 — [SECURITY.md](https://github.com/nodejs/node/blob/main/SECURITY.md)
- A doc note on the model's weakness was added in 22.7.0 and 20.18.0 ([#54268](https://github.com/nodejs/node/pull/54268)) — [CHANGELOG_V22](https://github.com/nodejs/node/blob/main/doc/changelogs/CHANGELOG_V22.md)

### Inferences
- There is a tension. The model is officially "not a sandbox", yet bypasses are still fixed as CVEs, including a **High** one in 22.23.2 (CVE-2026-58043). Users should treat it as a guard against mistakes and keep up with security releases. For untrusted code they should rely on OS or container isolation, not on `--permission`.

### Gaps
- SECURITY.md on `main` does not name the "Permission Model" in its trusted and untrusted lists (only the "permission enforcement" phrase). I did not find a separate Security-team blog post on its threat model; the clearest statements are in permissions.md and PR #56201.
